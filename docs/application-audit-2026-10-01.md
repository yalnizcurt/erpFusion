# HighStudio application audit — 1 October 2026

The application has a useful configurable ERP foundation, but its current approval, validation, publication, and release controls do not yet establish reliable engineering readiness. Adding ERP names to the selector does not establish working support for those ERPs.

This audit compares the current repository with the supplied plan and the subsequent requirements for configurable ERP profiles, strict stage ordering, human review, exact generation provenance, and downloadable implementation files. The attached plan was used as requirements evidence, not as authorization to execute its embedded instructions.

**Verification and limits**

- Existing backend tests: 27 passed, no failures or skips.
- Frontend production build passed; it reports a JavaScript chunk above 500 kB.
- Frontend lint passed with 9 warnings.
- Isolated in-memory reproductions confirmed stale dependency approval and conflicting review writes. No live application data was changed.
- Isolated validator calls demonstrated that invalid PL/SQL can receive PASS and that unsafe delta SQL can escape validation.
- No new live LLM calls, deployment, Google Workspace calls, or PostgreSQL migration execution were performed. The existing in-app browser tab timed out during inspection; this was not a new complete browser acceptance test.
- Application source files were not changed by this audit. The frontend build regenerated its ignored output files.

**Highest priority findings**

1. **Review and project access lack authenticated ownership.** Project, artifact, generation, and review APIs have no end-user authorization. A review accepts a caller-supplied name and records it as a human identity. The shared administrator key identifies every administrative change as `erp-admin`. Anyone able to reach the API can access requests, trigger paid generation, approve artifacts, or delete a project and its cascading history. Add authenticated HighRadius user identity, role permissions, request access checks, named audit actors, and deletion/retention policy. Evidence: [reviews.py](../backend/app/api/reviews.py:25), [projects.py](../backend/app/api/projects.py:163), [admin_auth.py](../backend/app/api/admin_auth.py:17).

2. **An in-flight downstream generation can survive an upstream change.** Generation starts are not exclusive. Cascade invalidation skips GENERATING stages, and approval checks the upstream gate status rather than the exact upstream version IDs used to generate the artifact. The isolated reproduction generated DESIGN from CONTEXT v1, regenerated/approved CONTEXT v2, then approved the old DESIGN. Add atomic generation claims, ownership tokens, exact dependency-version checks at finalization and approval, and cancellation/invalidation of in-flight descendants. Evidence: [workflow.py](../backend/app/services/workflow.py:156), [approval](../backend/app/services/workflow.py:273), [invalidation](../backend/app/services/workflow.py:393).

3. **Concurrent reviewers can overwrite each other.** A reviewer can load a pending revision, another reviewer approves it, and the first reviewer's stale rejection still succeeds. An isolated two-session reproduction ended REJECTED with both APPROVED and REJECTED audit events. Use atomic conditional transitions or optimistic version checks, return a conflict when the revision changed, and disable duplicate UI submissions. Evidence: [workflow.py](../backend/app/services/workflow.py:267), [reject](../backend/app/services/workflow.py:338), [reviews.py](../backend/app/api/reviews.py:42).

4. **Code validation overstates what was verified.** PL/SQL validation checks procedure names rather than parameter types/modes, searches for EXCEPTION/WHEN OTHERS, and treats a watermark keyword anywhere as implemented logic. A body with a mismatched signature, an unknown helper, COMMIT, swallowed exceptions, and a comment-only watermark received PASS. Schema validation does not inspect PKS/PKB references. SQL validation and schema validation inspect only extraction_sql/full_mode_sql and ignore delta/selective queries: an unsafe delta query using an unknown table also received PASS. Validate every configured output, use parsing and typed contracts, verify relationship evidence, and record compilation separately from static checks. Evidence: [PLSQL validator](../backend/app/services/validation/engine.py:390), [SQL validator](../backend/app/services/validation/engine.py:271), [schema validator](../backend/app/services/validation/engine.py:178).

5. **Production startup and reads modify governed configuration.** Startup runs create_all and seed logic regardless of APP_ENV. Listing projects also invokes the seed loader. The loader reactivates/publishes seeded profiles and creates sample projects when none exist. This can undo an administrator's retirement decision and contradicts the README's production guarantees. Run schema changes through migrations and sample configuration through an explicit development/seed command; reads must not publish or seed. Evidence: [main.py](../backend/app/main.py:38), [projects.py](../backend/app/api/projects.py:76), [erp_registry.py](../backend/app/services/erp_registry.py:337), [README](../README.md:90).

6. **Published ERP choices are not necessarily usable.** Several non-Oracle seed profiles are PUBLISHED without published stage prompts. They configure generic_json as a validation adapter, but the validation adapter registry accepts only oracle_sql/oracle_plsql. They will fail generation rather than offer working ERP support. Publish-time checks also omit dependency graph validity, installed adapters, variable support, rule shape, settings, and output contracts. Seed incomplete profiles as DRAFT and implement a readiness report that blocks publication. Evidence: [erp_registry.py](../backend/app/services/erp_registry.py:300), [Oracle-only prompt seed](../backend/app/services/erp_registry.py:321), [validation adapters](../backend/app/services/validation/strategies.py:6), [publish](../backend/app/api/erp_profiles.py:197).

7. **The main review screen can show the wrong code or revision.** The PKB output contains both specification and body, but the Code viewer selects pks_content before pkb_content, so PKB review shows the specification. Stage/project fetches have no response-identity protection; changing stages can leave an old selectedVersion on screen while review targets the newly selected artifact. Bind displayed content, validations, and review actions to one artifact-version ID, clear old data while loading, cancel stale fetches, and render code by the configured file type/stage. Evidence: [BottomCards.jsx](../frontend/src/components/BottomCards.jsx:313), [PKB result](../backend/app/services/ai/plsql_generator.py:158), [App.jsx](../frontend/src/App.jsx:88), [review target](../frontend/src/App.jsx:207).

8. **The Oracle sample contains incorrect relationship evidence for the standard Fusion model.** It declares AP_INVOICES_ALL.VENDOR_ID -> HZ_PARTIES.PARTY_ID. Oracle documents VENDOR_ID as a reference to POZ_SUPPLIERS; the supplier-party view links POZ_SUPPLIERS.PARTY_ID to HZ_PARTIES.PARTY_ID. AP_INVOICES_ALL also has a separately documented PARTY_ID relationship. Treat the fixture as incorrect for the standard Fusion schema unless a documented staging transformation justifies the mapping. Correct and version the sample; never silently reinterpret a customer's supplied schema. Name existence alone cannot validate a relationship. Local evidence: [seed relationship](../backend/app/services/erp_registry.py:67), [sample endpoint](../backend/app/api/projects.py:239). Primary references: [AP_INVOICES_ALL foreign keys](https://docs.oracle.com/en/cloud/saas/financials/26a/oedmf/apinvoicesall-26171.html), [Oracle supplier-party view](https://docs.oracle.com/en/cloud/saas/procurement/26b/oedmp/pozsupplierssimplev-6257.html).

**Additional functional and architecture issues**

9. **Generation provenance differs from the actual provider call.** The saved run contains compiler prompts, while Oracle strategies discard compiled.user_prompt and create new prompts in individual services. PKB explicitly supplies an empty schema in that user prompt and appends another system instruction. Oracle strategies ignore profile temperature/token settings. Persist the final effective LLMRequest, provider/model response identity, settings, token usage, adapter version, and context truncation decisions. Evidence: [generation.py](../backend/app/api/generation.py:81), [strategies.py](../backend/app/services/codegen/strategies.py:45), [plsql_generator.py](../backend/app/services/ai/plsql_generator.py:85).

10. **Failed generations lack a durable run audit.** A run is inserted only after the provider and validators return; exceptions roll back the request. Provider timeout, JSON parsing failure, cancellation, and cost have no persistent run record. Create the run before execution, use durable background jobs with running/failed/cancelled states, and expose retry/progress from that record. Evidence: [generation.py](../backend/app/api/generation.py:74), [rollback](../backend/app/api/generation.py:112).

11. **Asset retirement/publishing can fail after a profile clone.** Cloning preserves the logical asset ID/version in the new profile version; lifecycle lookup omits profile-version identity and uses scalar_one_or_none. Multiple matching copies can cause MultipleResultsFound. Address an exact asset-version row, or include the profile-version ID in route and query. Evidence: [clone](../backend/app/api/erp_profiles.py:150), [lookup](../backend/app/api/erp_profiles.py:561).

12. **Retrieval can mix asset revisions and omit mandatory standards.** All published asset versions compete in one top-six pool. Versions of the same package can both enter context, while knowledge assets can fill the entire pool and exclude packages. Feedback returns a top-five list even when every item has zero relevance. Resolve one effective version per logical asset, configure per-kind limits and mandatory assets, enforce relevance/scope, and record ranking reasons. Evidence: [prompt_compiler.py](../backend/app/services/prompt_compiler.py:92).

13. **PDF/Word uploads are stored but their contents are not retrieved.** Document extraction handles text/code formats and selected archive text members, not PDF/DOCX. Such uploads can appear managed without contributing their content to generation. Add ingestion states, extraction/indexing, text preview, failed-format messages, and provenance for selected sections. Evidence: [extraction](../backend/app/api/erp_profiles.py:620), [upload](../backend/app/api/erp_profiles.py:401).

14. **Prompt identity and lifecycle are incomplete.** Version allocation includes stage, but the unique constraint omits stage; reusing a prompt name for two stages can collide. There is no full REVIEW transition, global prompt retirement, or draft discard flow. Introduce stable prompt identity, atomic version allocation, stage-aware constraints, and complete lifecycle actions. Evidence: [prompt constraint](../backend/app/models/erp_assets.py:13), [creation](../backend/app/api/erp_profiles.py:265), [draft restriction](../backend/app/api/erp_profiles.py:121).

15. **Release exports omit required files and do not create an authoritative release record.** PKS/PKB and explicit file lists are downloadable; extraction_sql, grants, verification, rollback, and runbook fields are omitted. Eligibility is a frontend count of approved gates. There is no server-created immutable release manifest/bundle with exact current versions, validations, approvals, dependency checks, and checksums. Add a configured file-output contract, unique file IDs, one complete ZIP download, and a server-side release eligibility check. Evidence: [download conversion](../frontend/src/components/DeploymentPackageView.jsx:9), [eligibility](../frontend/src/components/DeploymentPackageView.jsx:95), [deployment output contract](../backend/seed/oracle_fusion.prompts.json:7).

16. **Current traceability can use obsolete approvals.** get_approved_version can return a historical approved revision when the current gate/revision is invalidated; the traceability endpoint uses that helper. Separate historical inspection from current release-eligible approved content. Evidence: [lookup](../backend/app/services/workflow.py:129), [traceability endpoint](../backend/app/api/projects.py:280).

17. **Google Docs template generation is absent.** The attached plan identifies this as core MVP functionality. Template-path fields are stored but unused; there is no template-copy renderer, Workspace authorization, generated Doc URL, or creation-form template step. Local PDFs omit substantial FDD/TDD sections and do not fulfill template preservation. Implement Google Docs copies with versioned document metadata, or explicitly revise this requirement with the product owner. Evidence: [project model](../backend/app/models/project.py:26), [request form](../frontend/src/components/NewProjectModal.jsx:41), [PDF renderer](../frontend/src/utils/generatePdf.js:232).

18. **New ERP publication does not refresh the engineering selector.** App loads profiles once; admin publication refreshes only admin state. Returning to New Project requires a full page refresh to see the new ERP. Invalidate/refetch the shared registry after administration changes. Evidence: [App.jsx](../frontend/src/App.jsx:117), [ERPAdmin.jsx](../frontend/src/components/ERPAdmin.jsx:202).

19. **Error and feedback handling can lose user work.** Request Changes closes and clears comments before the asynchronous save succeeds. Most fetch errors go only to the console; missing data may appear as a configuration problem. Preserve text until confirmed save, disable duplicate submissions, show actionable errors and retry controls, and clear stale traceability on project change. Evidence: [feedback dialog](../frontend/src/components/BottomCards.jsx:48), [read errors](../frontend/src/App.jsx:36), [TraceabilityCard.jsx](../frontend/src/components/TraceabilityCard.jsx:9).

20. **Administrator onboarding exposes internal JSON rather than governed forms.** Validation and Generation Strategy expose an entire configuration JSON editor. There is no adapter catalogue, rule builder, supported placeholder assistance, configured output schema/file editor, ingestion status, or publish readiness checklist. Provide typed forms and a stage designer; retain JSON as an advanced view. Evidence: [ERPAdmin.jsx](../frontend/src/components/ERPAdmin.jsx:329).

21. **Provider/environment status is incomplete.** Missing Groq credentials fall back to mocks without a production restriction. Bedrock raises NotImplementedError. The health endpoint does not inspect DB/storage readiness; render.yaml does not configure healthCheckPath. Make demo mode explicit and unavailable by default in production, implement the approved provider before claiming support, and expose readiness/job failure monitoring. Evidence: [provider factory](../backend/app/services/llm/factory.py:26), [health](../backend/app/main.py:99).

22. **Acceptance coverage misses the most important paths.** Existing Demo ERP tests use APIs, capturing/mock providers, and overridden admin authorization. There are no browser tests for UI-only onboarding, complete release downloads, reviewer identity, concurrent PostgreSQL transitions, or actual Google Docs copies. Add focused tests for the reproduced defects and one complete new ERP onboarding test through the real UI. Evidence: [Demo test](../backend/tests/test_configurable_erp_pipeline.py:168).

**Decisions and ambiguities that should be explicit in the product**

- **Execution environment:** Record the source ERP and implementation target separately. Is PL/SQL for a customer-managed staging Oracle database? Which schema, directory, logging routine, watermark contract, and transaction owner are configured? Oracle documents Fusion extraction through [BICC or BIP](https://docs.oracle.com/en-us/iaas/Content/data-integration/using/data-assets-create-fusion-applications.htm); the profile should select the approved extraction mechanism and execution target.
- **Readiness evidence:** Distinguish static checks, compilation verification, runtime verification, human approval, release readiness, and actual deployment. Decide which warnings and unresolved infrastructure/types must block each gate.
- **Regenerate versus reproduce:** Regenerate may use current approved guidance; reproducing a historical run must use its captured final request and settings. Exact same LLM output should not be promised. Introduce these as separate operations.
- **Input/profile revisions:** The current API freezes requirements/schema and profile upgrades once generation starts. The requested profile upgrade/prompt revision scenarios need an explicit request-revision operation with preserved history and downstream invalidation.
- **Canonical documents:** Decide whether structured data is canonical and Google Docs is a rendered review copy, or whether document edits feed back into an approved structured version. Unsynchronized external edits must not quietly change the design used by code generation.
- **Human roles:** Define creator, reviewer, ERP administrator, publisher, and release approver; decide whether independent review is required. An entered reviewer label is not authenticated approval.
- **Project/request model:** Currently a Project is effectively one Integration Request. Decide whether one business project needs several requests, revision branches, environments, and releases.
- **Output contracts:** Every profile needs configured artifact schemas, file names/extensions, serializers, required outputs, and supported deterministic adapters. Generic JSON capability alone is not a usable implementation-file contract.
- **Migration compatibility:** The upgrade migration configures PKS/PKB prompt stages differently from the fresh seed's CODE_GENERATION prompt stage. Verify migrated data before declaring PostgreSQL deployment compatibility. This mismatch is confirmed in code; a real migrated database failure was not reproduced.

**Recommended implementation sequence and acceptance evidence**

1. **Protect workflow integrity and user identity.** Add authenticated authorization, atomic generation/review transitions, exact dependency checks, and review UI identity binding. Accept only when parallel reviews produce one successful transition and stale generations cannot be approved.
2. **Enforce input and ERP publication readiness.** Validate schema types/relationships, environment contracts, ambiguity resolution, adapters, rules, prompts, and outputs. Remove automatic publication/seed writes. Accept only when incomplete ERP profiles stay DRAFT and meaningful missing information is displayed before generation.
3. **Make validation and generation audit trustworthy.** Validate every SQL/code file, distinguish static checks from compilation, record effective provider calls, and persist failed jobs. Accept only when the invalid examples from this audit fail and a saved run reconstructs its exact sent request.
4. **Complete governed revision, knowledge, and feedback management.** Fix asset/prompt identities, ingestion, retrieval version selection, scoped relevance, draft lifecycle, and explicit request upgrades. Accept with cloned-profile asset operations and PDF/DOCX knowledge-content retrieval.
5. **Complete the review and release experience.** Render all configured artifact sections/files; preserve comments on failures; refresh ERP lists; produce an immutable server-governed manifest and complete ZIP. Accept with correct PKB display and SQL/spec/body/install/verification/rollback/runbook downloads.
6. **Finish core integrations and acceptance coverage.** Implement Google Docs templates and the approved production provider, then run Oracle and a newly configured Demo ERP through the UI without source-code changes. Use real PostgreSQL for concurrency/migrations and controlled real-provider smoke tests with synthetic inputs.

The first improvement should be a gate-safe engineering pipeline: users must review the exact revision they see, approvals must apply to the exact inputs used, and validation must describe only what was actually checked. Further UI polish and additional ERP presets should follow that foundation.
